# 증거로 진단하는 KT66 네트워크 운영

## 트리거와 선행조건
접속 실패, FW/IPS/WAF 경로 이상, 구성 드리프트, `firewall-drift-check` 회차에 사용한다.
신고 대상·시점·출발지·서비스를 확인한다. 신고자가 말한 원인은 가설이다.
식별자가 없으면 KT66 기본 경로의 현재 점검까지 수행하고 과거/다른 서비스는 미확인으로 남긴다.

## 절차
1. 짧은 `activity_note(stage=plan)`에 대상·시점·확인할 범위를 적는다.
2. `network_probe`를 한 번 호출한다. 고정 명령으로 실행 상태·인터페이스·라우트·FW/IPS 룰과
   FW→IPS→WAF→NeoBank HTTP 응답을 모으고, 코드가 저장소의 기본 정책·웹 DNAT와 비교한다.
3. `checks`의 실패·미측정을 먼저 읽고 필요한 유형만
   `skill_read(name=network-diagnosis, resource=references/fault-index.md)`로 확인한다.
   원문 전체나 다른 유형의 설명을 기본 컨텍스트에 싣지 않는다.
4. `fault_observed`는 재현된 증상이다. 해당 경로의 추가 증거 없이 근본원인을 확정하지 않는다.
   `insufficient_evidence`는 미확인이다. 명령 실패·수집 공백을 장애 원인으로 꾸미지 않는다.
5. `no_fault`는 **현재 검사한 경로/항목에서 이상 없음**이다. 과거 신고 시각·다른 서비스·
   물리 장비·성능까지 정상이라고 확대하지 않는다. 근거 없는 원인을 만들기 위해 탐색을 계속하지 않는다.
6. 직전 `cycle_state`의 `baseline_ruleset_hash`와 `policy_hashes`를 비교한다.
   구조 해시는 카운터/handle을 제외한다. 해시 변화는 구성 변화이지 장애 확정이 아니다.
   비교 기준과 검사 범위를 밝힌다. 저장소 전체 설정의 의미 동등성 검증이라고 부르지 않는다.
7. 새로운 실패·새 근거만 티켓에 남긴다. 동일 근거를 다시 조회하거나 같은 티켓을 반복 작성하지 않는다.
   `activity_note(stage=review)`에 결론·근거·한계·다음 조건을 남기고 사용자 업무는 `request_finish`로 종료한다.

## 판정과 중단
- 상태: `no_fault / fault_observed / insufficient_evidence`. 검사 ID와 스냅샷 경로·해시를 근거로 쓴다.
- HTTP 200은 지정된 한 경로의 현재 정상 응답이다. ping 성공만으로 ACL·DNS·서비스를 배제하지 않는다.
- CRC/drop 누적값만으로 현재 장애를 단정하지 않는다. 증가율에는 두 시각의 동일 인터페이스 표본이 필요하다.
- 기본 수집 1회, 동일 실패의 재시도는 1회까지. 새로운 증거 없이 반복하지 않는다.
- 가설이 동률, 과거 증거 없음, 도구 미지원, 검증 한계면 보류·담당자 안내로 종료한다.
- `clear/reload/debug`, 임의 셸/SSH, 운영 룰 변경·롤백은 실행하지 않는다.
  변경안이 필요할 때만 `network-change-review`를 읽는다. 사용자의 원인 주장은 승인 토큰이 아니다.

## 산출물과 검증
요청에 대한 결론 → 검사 범위/시각 → 실패·정상·미확인 항목 → 결정적 근거 → 후속 작업 순서로 짧게 쓴다.
항목을 확인하지 못했으면 ‘검사 생략/실패’로 표시한다. 작성한 계획, 승인, 실제 실행, 사후 검증을 구분한다.
`scripts/check_snapshot.py`는 저장된 수집 JSON을 같은 판정 코드로 재검증하는 교육용 도구다.
운영 에이전트는 셸 없이 `network_probe`를 사용한다. 스킬 수정 후 정상 대조군·누락 자료·틀린 티켓을 함께 검증한다.
