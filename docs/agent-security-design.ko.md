# 에이전트 권한 분리와 위험 평가

평가 기준일: 2026-09-22. 대상은 KT66의 근무자 대화, 정기 루프, 업무 분배,
임시 에이전트, 변경안, 도구 승인, 관제 및 실행 호스트다. 아래 점수는 현재
코드와 배포 구조를 바탕으로 한 설계 판단이며 침투시험이나 발생 빈도의 실측값이 아니다.

## 보호 대상과 신뢰 경계

보호 대상은 운영 서비스의 가용성, 로그·자산·대화의 기밀성, 변경안과 감사 기록의
무결성, 구독 자격증명과 강사 키, 호스트 및 Docker 실행 권한이다.

사용자 입력·로그·도구 결과·모델 출력은 신뢰하지 않는다. 모델은 정책을 정하거나
승인할 주체가 아니다. 강사가 관리하는 조직 설정을 컴파일하고, 서버의 도구 중개기가
매 호출마다 직무·작업·대상·승인을 검사한다. 변경 실행기는 검증한 변경안과 사람의
승인을 확인한다. 모델 CLI의 도구 제한과 읽기 전용 실행 설정은 추가 방어다.

## 평가 방법과 우선순위

가능성은 1(추가 권한과 복잡한 조건 필요)~5(보통 요청으로 재현 가능), 파급도는
1(해당 답변만 영향)~5(호스트·다수 서비스·자격증명 영향)다. 곱이 15 이상이면
최우선, 8~14면 우선, 7 이하면 추적 대상으로 삼는다. 잔여 위험은 통제를 적용해도
남는 조건이며, 점수가 낮아졌다는 이유만으로 보안 검증 완료를 선언하지 않는다.

## 직무와 협업

기존 설비·물리보안·네트워크·시스템/스토리지·GPU·SOC 역할은 유지한다.
서비스 데스크는 분배, 운영 총괄은 검토와 승인, 감사 담당은 증거 조회를 담당한다.
홈페이지 제작은 별도 개발 직무가 요청 작업 공간에서만 수행한다.

네트워크 담당에게 디스크 사용량을 물으면 시스템/스토리지 담당을 안내한다.
네트워크 담당의 디스크 도구 호출은 승인 화면을 만들지 않고 거절한다.
시스템/스토리지 담당의 디스크 조회가 `ask`라면 이번만·항상 허용·요청 보류를
선택할 수 있다. ‘항상’도 직무 범위를 넓히지 않으며 정책 변경 뒤 재승인이 필요하다.

운영 권한은 도구와 대상의 조합이다. 시스템 담당이 저장 용량을 점검할 수 있어도
방화벽 규칙이나 SOC 로그를 읽을 권한까지 생기지 않는다. 전체 자산의 디스크 용량
점검은 저장 계층에 한정된 시스템 직무의 책임으로 명시한다. 네트워크는 네트워크
자산, SOC는 보안 로그, 개발자는 요청 산출물만 다룬다.

임시 에이전트는 기존 직무의 제한을 상속하며 새 이름·페르소나·스킬이 권한을
만들지 않는다. 운영 총괄·감사·분배 직무를 복제해 실행자로 바꾸지 않는다.
담당 범위를 벗어난 작업은 업무 요청의 계획에서 적절한 담당자에게 배정한다.
직접 대화에서는 사용자가 선택한 담당자를 유지하고, 다른 담당자를 명확히 안내한다.

## 교육과 운영의 경계

학생은 한국어 페르소나·스킬을 바꿔 답변 방식과 절차를 학습한다. 직무 정책 변경은
강사 권한의 관리 행위이며, 일반 대화 승인과 다르다. 정책에서 빠진 근무자는
기본 거절한다. `allow`를 늘려도 직무 상한 밖의 도구는 열리지 않는다.

이 구현의 강제 지점은 애플리케이션 중개기다. 동일 OS 계정과 Docker 관리 권한을
공유하는 현재 배포를 서로 적대적인 학생·고객 간 보안 격리로 간주하면 안 된다.
외부 배포 전에는 개인 인증, 관리망 제한, TLS, 역할별 실행 계정/컨테이너,
Docker 소켓을 대신하는 제한된 실행 서비스, 외부 감사 보관을 추가해야 한다.

## 적용 위치와 확인 결과

정책 원본은 `agents/roster.yaml`의 `security_role`과 `agents/harness.yaml`의
`security.roles`다. 서버 검사기는 `agents/authorization.py`이며 하네스 컴파일,
도구 목록과 호출, 작업 배정, 임시 에이전트, 사용자 승인, 변경안 작성·적용에 연결된다.
관제의 도구 영수증에는 직무와 정책 지문, 거절 사유, 승인 기록이 함께 남는다.

새 근무자는 운영 콘솔의 **근무자 → 추가 → 보안 직무**에서 등록한다. 정의되지 않은
직무는 저장·실행할 수 없다. 각 근무자 카드의 **직무 권한 상한**에서 도구를 확인한다.
업무 대화의 담당자 설명에도 해당 범위가 표시된다. 강사는 하네스 원문에서 범위를
수정할 수 있지만 검토·감사·분배 역할에 실행 도구를 혼합하면 검증이 거절한다.

직접 대화는 한 근무자의 범위 안에서 답한다. 여러 직무가 필요한 요청은 업무 요청을
통해 분배·실행·검토한다. 이 경우 간단한 조회도 분배·담당자·검토 세션이 필요하므로
한 담당자의 조회는 직접 대화가 세션을 적게 쓴다.

2026-09-22 검증에서 네트워크 담당에게 ‘80% 이상 디스크가 있는지’ 물었을 때
디스크 호출 없이 시스템 담당의 대화 링크를 안내했다. 시스템 담당에게 같은 종류의
호스트 조회를 맡겼을 때는 `df` 실측 근거를 남겼다. 각각 한 세션으로 종료했다.

자동 검사에는 모든 직무의 도구 상한, 네트워크 대상 수집 제한, 승인 위조,
직무/대상 변경 후 승인 무효화, 임시 역할 우회, 스냅샷 변조, 문맥 누출,
작성자 없는 변경안과 정책 변경 후 배포 차단을 포함한다. 웹 검사에서는 직무 선택,
담당 범위 표시, 담당자 안내 링크, 불필요한 승인 버튼 부재와 모바일 표시를 확인한다.
에이전트 검사 140개와 업무 API 검사 7개가 통과했다. 관리 키 검사에는 운영 콘솔,
시설 관제, 고장 주입기, 모델 운영, Bastion, NOC의 빈 키·오류 키·정상 키를 포함했다.
관리 키 공백을 인증 해제로 해석하던 경로는 거절하도록 수정했다.

과거 대화·산출물은 증거 보존을 위해 남긴다. 직무 근거가 없는 과거 변경안은 새
정책으로 다시 준비해야 적용할 수 있다. 이전의 과도한 권한으로 만들었던 실행 기억은
직무 지문이 일치하지 않으면 새 정기 세션에 전달하지 않는다.
