# KT66 교수·강사용 매뉴얼

이 문서는 실습 서버를 준비하고 수업·평가·복구를 운영하는 교수, 강사, 실습 조교를 위한 안내입니다. 학생이 배울 핵심은 **전문 업무를 자연어 절차로 표현하고, 에이전트의 실제 수행 증거로 그 절차를 개선하는 능력**입니다.

## 1. 수업 환경과 역할 배정

독립적인 지침 편집과 장애 주입을 하려면 **학생 또는 조별 전용 서버·VM**을 사용합니다. 한 인스턴스를 함께 쓰면 자산 상태·지침·요청·증거가 공유됩니다. 현재 강사 키는 개인별 학생 계정이나 세밀한 교육용 권한 체계를 대신하지 않습니다.

| 담당 | 준비·수행할 일 |
|---|---|
| 교수·강사 | 전문 업무 사례, 판단 기준, 담당 역할, 과제와 평가 기준 정의 |
| 조교·서버 관리자 | 설치, 구독 로그인, 접속 범위, 백업, 장애 원복, 실행 예산 관리 |
| 학생 | 기본 실행 관찰, 한국어 지침 수정, 같은 조건의 결과 비교, 근거 제출 |
| 에이전트 | 배정된 직무·도구 범위 안에서 조회·작업·보고 |

학생에게는 담당자와 대상 자산, 기간, 변경 가능한 파일, 허용된 작업, 제출물을 함께 제시합니다. 첫 수업은 조회와 보고 형식 변경으로 시작하고, 이후 사건 조사·협업·변경 검토로 확장합니다.

## 2. 새 서버 설치

### 2.1 사전 준비

이 절의 명령은 **Ubuntu 계열 Linux와 systemd를 사용하는 새 실습 호스트**, 일반 사용자 계정, `~/work/kt66` 경로를 기준으로 합니다.

- Docker Engine·Compose를 사용할 수 있는 Linux와 sudo 권한을 준비합니다. 호스트 네트워크·iptables·systemd를 사용하므로 다른 OS나 Docker Desktop을 동일하게 검증한 설치로 취급하지 않습니다.
- 전체 서비스에는 Wazuh와 여러 웹앱이 포함됩니다. 수업 계획의 출발점으로 RAM 32GB·여유 SSD 100GB 정도를 잡고 실제 실습 부하와 보관 기간으로 조정합니다. 이는 공식 최소 사양이나 성능 보장값이 아닙니다.
- 인터넷 연결은 이미지·패키지 설치와 구독 CLI 인증·실행에 필요합니다.
- 웹·관리 포트와 실습용 여섯 `/24` 대역이 기존 환경과 충돌하지 않는지 확인합니다. 대역은 [README의 존 표](../README.md#실제-인프라와-시설-시뮬레이션), 정확한 연결은 [Compose](../docker-compose.yaml)를 봅니다.
- 취약 앱, 장애 주입기, 관리 화면을 강의실 실습망에 한정합니다. 학생이 조회한 자료는 외부 구독 모델의 입력이 될 수 있으므로 수업용 자료를 사용합니다.
- 기존 Docker 서버라면 설치 스크립트의 Docker 재시작, `daemon.json` 변경, 선택적인 netplan 설정 영향을 먼저 검토합니다. 원격 IP 변경 실습에는 별도 콘솔을 준비합니다.

Ubuntu 예시 의존성 설치:

```bash
sudo apt-get update
sudo apt-get install -y git curl ca-certificates openssl jq nano python3 python3-yaml nodejs
python3 --version
node --version
```

Python은 3.10 이상을 사용합니다. Node.js는 정적 홈페이지의 JavaScript 구문 검사에 필요합니다. 사용할 CLI의 추가 요구 사항은 공식 설치 안내를 따릅니다.

### 2.2 저장소와 환경 설정

```bash
mkdir -p ~/work
git clone https://github.com/mrgrit/kt66.git ~/work/kt66
cd ~/work/kt66
cp .env.example .env
chmod 600 .env
nano .env
```

이미 배포한 환경에서는 `cp .env.example .env`를 다시 실행하지 않습니다.

| 항목 | 설정 방법 |
|---|---|
| `WEB_HOST_IP` | 학생 PC에서 접근 가능한 실습 서버의 실제 IP |
| `INT_HOST_IP` | 관리 화면을 바인딩할 서버 IP. 처음에는 같은 실습 LAN IP로 시작 |
| `API_KEY` | `replace-with-a-random-control-key`를 서버마다 다른 긴 임의 값으로 교체 |
| `SSH_USER / SSH_PASS` | 실습용 계정·비밀번호로 교체 |
| `TZ` | 컨테이너 시간대. 기본 `Asia/Seoul` |
| `AICOMPANION_LLM_BACKEND` | 기본 `mock`. AICompanion의 백엔드이며 근무자 구독 로그인과 별개 |
| `LLM_BASE_URL` | 모델 운영·기존 Bastion 등의 선택적 Ollama 연결 주소. 현재 근무자의 런타임·모델은 `agents/roster.yaml`에서 선택 |

`openssl rand -hex 32`로 제어 키 후보를 만들 수 있습니다. 키와 로그인 자료를 학생 제출물이나 Git에 포함하지 않습니다. 루프의 예약 시간대는 별도로 `agents/harness.yaml`의 `execution.timezone`에서 결정합니다. 포트를 바꿀 때는 `.env.example`의 오래된 설명에만 의존하지 말고 Compose의 해당 `ports` 변수명을 확인합니다.

### 2.3 인프라 기동

일반 사용자 계정에서 실행합니다. 필요한 단계는 스크립트가 sudo를 사용합니다.

```bash
./kt66.sh install
./kt66.sh up
docker compose -f docker-compose.yaml ps -a
sudo ./kt66-net.sh --check
```

`install`은 Docker가 없으면 설치하고, Docker 데몬의 `userland-proxy=false`와 DNS 설정을 적용한 뒤 재시작합니다. 실제 IP를 고정하는 netplan 단계는 별도 확인을 받습니다. Docker 그룹이 새로 추가되었거나 일반 사용자로 `docker ps`가 거절되면 계정의 그룹 설정을 확인하고 재로그인합니다. **근무자 러너도 같은 일반 계정으로 Docker를 사용할 수 있어야 합니다.**

`up`은 다음을 준비합니다.

1. 누락된 SSH 키와 Wazuh 실습 인증서.
2. Compose 이미지 빌드와 컨테이너 기동.
3. 호스트 IP·브리지 사이의 네트워크 설정.
4. `kt66-hostip`·`kt66-net` 시스템 서비스.
5. Sigma 적재와 콘솔 접속 점검.

AI 근무자용 **`kt66-runner` 사용자 서비스는 다음 절에서 별도로 설치**합니다. Compose의 `netglue`, `agent-observer-setup`처럼 한 번 실행하고 정상 종료하는 서비스도 있으므로 “모든 컨테이너가 running이어야 성공”으로 판단하지 않습니다.

에이전트 SIEM 수집은 `agent-observer`가 수행합니다. 전용 인덱스와 수집·조회 계정은 초기화 서비스가 준비하며, xOC 대시보드에서 전송 대기·오류·최근 수집을 확인합니다. 기존 서버 추가 설치·보존·백업과 수업 예시는 [리스크 지도와 xOC·SOC 관제](OBSERVABILITY.ko.md)에 있습니다. 과거 적재가 끝나기 전 통계를 전체 기준선으로 삼지 않습니다.

Wazuh 자체에서 수업을 진행하려면 [에이전트 관제 매뉴얼](WAZUH-AGENT-MONITORING.ko.md)을 따릅니다. v2 필드 매핑 업그레이드, 학생 계정 범위, 가져오기용 검색·대시보드 15개, 사건 추적·스킬 성과 비교 실습을 제공합니다. 원본에 없던 과거 실행 시간이나 위임 부모는 미측정으로 남습니다.

### 2.4 외부 GPU 연결은 선택 사항

기본 관제·보안·에이전트 지침 수업에 외부 GPU가 필수는 아닙니다. GPU 실측과 실제 추론 부하 실습에는 별도 GPU 서버·모델 서비스·접속 설정이 필요합니다.

[gpu-gw/setup-tunnel.sh](../gpu-gw/setup-tunnel.sh)는 랩과 GPU 서버 양쪽의 WireGuard 설정을 생성합니다. 생성 파일을 원격 서버에 적용하고, 자산 대장·서비스 주소·지표 수집을 확인해야 연결이 완성됩니다. 단순히 스크립트를 실행했다고 GPU가 준비된 것은 아닙니다. 터널 주소·GPU 측 기본값을 수업망에 맞추고, 생성된 키는 서버별로 관리합니다.

## 3. 구독 계정과 에이전트 러너

### 3.1 어느 계정으로 로그인하나요?

**KT66 러너를 실행하는 호스트의 일반 사용자 계정**으로 설치·로그인합니다. root나 다른 계정에서만 로그인하면 사용자 서비스가 그 인증 자료를 사용할 수 없습니다. 웹 강사 패널에 모델 계정을 등록하는 화면은 현재 없습니다.

기본 명단은 Claude 6명, Codex 7명입니다. 두 CLI를 준비하거나 근무자 운영 화면에서 사용 가능한 런타임·모델로 명단을 조정합니다. 역할 지침을 공유해도 모델별 결과와 사용량은 달라질 수 있습니다.

- `.env`의 `API_KEY`: KT66 제어·강사 키.
- Claude·ChatGPT 로그인: 근무자 모델 세션 인증.
- GPU/Ollama 연결: 학생이 운영할 AI 서비스.

이 세 설정은 서로 대체하지 않습니다.

### 3.2 CLI 설치와 로그인

설치는 [Claude Code 공식 시작 안내](https://code.claude.com/docs/en/quickstart)와 [Codex CLI 공식 안내](https://learn.chatgpt.com/docs/codex/cli)를 따릅니다. 설치 후 다음 명령이 **서비스를 운영할 계정**의 터미널에서 실행되어야 합니다.

```bash
command -v claude
command -v codex
claude --version
codex --version
```

KT66의 구독 실행 경로에 맞춰 로그인합니다. 다음 Claude 명령은 현재 프로젝트 운영 안내에서 사용하는 CLI 명령입니다. 설치 버전에서 옵션이 다르면 `claude auth login --help`와 공식 문서를 확인합니다.

```bash
claude auth login --claudeai
codex login
```

원격 서버에서 Codex의 브라우저 콜백을 받을 수 없다면 `codex login --device-auth`를 사용할 수 있습니다. 계정·워크스페이스에서 기기 코드 로그인이 허용되어야 합니다. [Codex 인증 안내](https://learn.chatgpt.com/docs/auth)

로그인 후 상태를 확인합니다.

```bash
claude --setting-sources "" --settings '{"disableAllHooks":true}' auth status
codex login status
```

Claude는 `claude.ai` 인증, Codex는 ChatGPT 인증인지 확인합니다. 결과에 계정 정보가 포함될 수 있으므로 공유 자료에서는 가립니다. KT66 근무자 실행은 직접 모델 API 키와 자동 API 전환을 사용하지 않습니다. 사용할 모델에 대한 계정의 접근 권한과 구독 한도는 별도로 적용됩니다.

### 3.3 기본 예산을 정한 뒤 러너 시작

[agents/harness.yaml](../agents/harness.yaml)의 `execution`을 먼저 검토합니다.

| 설정 | 의미와 기본값 |
|---|---|
| `timezone` | 예약 시간대, `Asia/Seoul` |
| `max_concurrent_sessions` | 전체 동시 세션 수, `2` |
| `daily_session_limit` | 최근 24시간 세션 시도 상한, 기본 `null`은 별도 로컬 상한 없음 |
| `max_attempts` | 작업 시도 상한, `2` |
| `quota_backoff_sec` | 구독 한도 응답 뒤 대기, `900`초 |
| `adaptive` | 무변화 감시의 점검 간격·안정화·중복 억제 |

수업에서는 계정 한도와 과제 규모에 맞춰 `daily_session_limit`를 정합니다. 업무 요청의 세션 예산도 별도로 적용됩니다. 토큰 통계는 계정의 잔여 구독량이나 청구 금액이 아닙니다.

기본 설치 위치 `~/work/kt66`에서 다음을 실행합니다.

```bash
python3 agents/agentctl list
python3 agents/agentctl render --all
mkdir -p ~/.config/systemd/user
cp agents/kt66-runner.service ~/.config/systemd/user/
nano ~/.config/systemd/user/kt66-runner.service
```

서비스 파일에서 다음 세 항목을 확인합니다.

| 항목 | 확인 내용 |
|---|---|
| `WorkingDirectory` | 기본 `%h/work/kt66`가 실제 저장소 위치와 같은지 |
| `ExecStart` | 기본 `/usr/bin/python3 %h/work/kt66/agents/loop_engine.py`의 Python에 PyYAML이 있는지 |
| `Environment=PATH` | `command -v`로 확인한 Claude·Codex·Node·Docker 경로가 포함되는지 |

`%h`는 해당 사용자의 홈입니다. systemd 사용자 서비스는 대화형 셸의 초기화 파일이나 nvm 설정을 자동 실행하지 않습니다. 설치 경로가 다르면 실제 절대 경로를 사용합니다.

```bash
systemctl --user daemon-reload
systemctl --user enable --now kt66-runner.service
systemctl --user status kt66-runner.service
journalctl --user -u kt66-runner.service -n 80 --no-pager
```

무인 서버에서 로그아웃 후에도 유지하려면 관리자가 `sudo loginctl enable-linger <러너 사용자명>`을 설정합니다. 같은 환경에 systemd와 별도의 `cc-runner --watch` 프로세스를 중복 실행하지 않습니다.

## 4. 접속과 설치 완료 확인

학생은 `http://<INT_HOST_IP>:8020/`에서 시작합니다. 업무 요청은 `:8050/requests`, Wazuh는 **HTTPS** `:5601`입니다. 전체 주소는 [README 접속 표](../README.md#접속과-기본-사용법)를 봅니다.

이름으로 접속하려면 학생 PC의 hosts 파일에 다음 한 줄을 넣습니다. `<서버 실제 IP>`를 `WEB_HOST_IP`로 바꿉니다.

```text
<서버 실제 IP> noc.kt66.lab injector.kt66.lab envsim.kt66.lab agentops.kt66.lab modelops.kt66.lab infraops.kt66.lab
```

Linux/macOS는 `/etc/hosts`, Windows는 `C:\Windows\System32\drivers\etc\hosts`입니다. 이 경로는 [관리 콘솔 vhost](../web/vhosts/120-datacenter.conf)를 사용하며 ModSecurity 실습 검사를 끕니다. 이름을 붙이는 것만으로 관리 화면 접근이 제한되지는 않습니다.

설치 완료는 다음으로 판정합니다.

1. 학생 PC에서 NOC가 열리고 자산·층·경보가 조회된다.
2. 일반 사용자로 Docker 상태를 볼 수 있고 호스트 네트워크 점검이 통과한다.
3. 근무자 운영에서 명단·루프·하네스 활성 상태와 러너 heartbeat를 확인한다.
4. 조회 전용 질문 한 건을 담당자에게 보내 실제 도구 결과와 실행 증거를 확인한다.
5. 실행 실패, 자료 미수집, 구독 로그인 오류를 정상으로 표시하지 않는지 확인한다.

확인용 질문 예: 시스템 담당에게 “현재 등록된 시스템의 디스크 사용량을 표로 보여 주고, 측정하지 못한 대상도 적어 줘.” 이 단계부터 구독 세션을 사용합니다. GPU 미연결이나 짧은 로그 보관 기간은 따로 기록합니다.

## 5. 수업을 설계하는 방법

### 5.1 한 차시의 진행 예

| 단계 | 강사의 준비 | 학생 활동 |
|---|---|---|
| 업무 소개 | 전문가가 실제로 보는 자료와 판단 기준 제시 | 대상·기간·완료 조건을 자기 말로 정리 |
| 기본 실행 | 같은 입력과 기본 지침 제공 | 응답·사용한 스킬·도구 기록 보존 |
| 지침 수정 | 이번에 바꿀 판단 한 가지 지정 | 해당 파일의 한국어 본문만 수정 |
| 재실행 | 동일 입력·같은 모델·새 대화 조건 유지 | 수정 전후 조회·판단·보고 차이 비교 |
| 근거 검토 | 정답과 반증 자료, 누락 사례 제시 | 잘된 점·과장·미수행·권한 경계 설명 |
| 정리 | 다음 개선 과제와 복구 기준 제시 | 변경 파일·증거·결론 제출 후 원복 |

첫 과제는 “결론·근거·한계로 보고하기”, 다음 과제는 “정상 판단 전에 반대 증거 확인하기”처럼 범위를 좁힙니다. 실시간 상태가 변하는 과제는 관측 시각을 고정하거나 같은 모의 자료를 제공해야 지침 효과를 비교하기 쉽습니다.

### 5.3 에이전트 지침 수업의 운영 원칙

학생에게 “모든 문서를 수정하라” 대신 **업무 한 가지와 수정할 파일 한 개**를 배정합니다. 절차는 `SKILL.md`, 선택 기준은 persona, 일정은 루프, 모델·담당 연결은 roster, 실제 권한은 harness에 둡니다.

웹 편집은 **근무자 운영 → 근무자·R&R → R&R·스킬·담당 설정**, **일하는 방식 → 스킬 라이브러리**를 사용합니다. 스킬을 추가·수정·삭제하고 근무자에 연결할 수 있습니다. **적용**에서 원본·생성 사본의 일치와 백업 복원을 확인합니다. [화면·파일 대응 및 조작 순서](AGENT-CONFIGURATION.ko.md)를 함께 배포하세요. 스킬 연결은 실제 직무 권한을 늘리지 않습니다.

SOC 수업은 [학생용 기본 예제](STUDENT-GUIDE.ko.md#soc-defaults)부터 진행합니다. 단순 경보 조회에 30개 지표 종합 분석을 요구하지 않고, 질문에 맞는 절차를 고르는 것도 평가합니다.

월간 분석·규칙 관리 예시는 `agents/examples/soc/`에 있고 자동 실행되지 않습니다. 파일을 활성 경로와 roster에 연결하면 실제 예약 세션이 발생합니다. 전체 집계·평판·위협정보·규칙 등록 도구가 필요한 단계는 학생이 “문서만으로 구현됐다”고 보고하지 않도록 지도합니다.

지침 저장은 즉시 모델 호출을 만들지 않습니다. 다만 역할에 연결된 스킬·정책 수정은 기존 세션의 다음 도구 접근을 중단시킬 수 있으므로 **실행 중인 작업이 없는 시점**에 수정합니다.

## 6. 장애 주입과 복구 실습

`envsim`은 시설 시뮬레이션을, `injector`는 실습 컨테이너·네트워크에 대한 실제 조작을 담당합니다. NOC 강사 패널에서 두 영역을 함께 사용할 수 있습니다.

1. 대상 자산과 정상 상태, 복구 방법을 기록합니다.
2. 학생에게 공개할 증상과 비공개 평가 기준을 나눕니다.
3. 카탈로그에서 허용 대상·영향·유지 시간·원복 방법을 확인하고 한 건만 주입합니다.
4. 실제 경보와 도구 관측이 나타났는지 확인한 뒤 학생에게 조사하게 합니다.
5. 학생의 판정·조치 제안·승인·사후 검증을 수집합니다.
6. 해당 주입을 해제하고 서비스·네트워크·경보를 다시 확인합니다.

IT 주입기의 `state` 유형은 상태를 유지하고, 설정된 TTL이 있으면 만료 후 원복합니다. `action` 유형은 일회성 행위이며 목록에서 사라져도 이미 발생한 트래픽·로그까지 없어지는 것은 아닙니다. 시설 고장도 IT 주입기와 같은 TTL 동작이라고 가정하지 말고 해제와 정상 복귀를 확인합니다.

에이전트가 직접 해제할 수 있는 범위는 구현된 **담당 가상 설비 고장**과 그 승인 정책에 한정됩니다. 임의의 실제 서비스 정지·방화벽 변경을 자동 수행하는 범용 운영 권한은 없습니다. 홈페이지·WAF 변경안은 별도의 사람 승인 경로를 사용합니다.

연쇄 장애 수업에서는 설비 모델의 영향과 실제 서버 상태 변화를 구분해 기록합니다. 모든 `cascade` 선언이 자동으로 다음 장애를 발생시키는 구현은 아닙니다.

## 7. 평가와 제출물

글이 유창하거나 “해결 완료”라고 답했다는 이유만으로 성공으로 채점하지 않습니다. [AI 에이전트 관제](AGENT-CONTROL.ko.md)의 에이전트 보고, 도구 관측, 실행기 기록을 구분해 평가합니다.

| 평가 항목 | 배점 예 | 확인할 증거 |
|---|---:|---|
| 업무 범위와 완료 조건 | 15 | 대상·기간·자료·담당 역할 |
| 절차·판단 기준 | 25 | 수정한 지침, 조사 순서와 반증·보류 조건 |
| 실행과 검증 | 25 | 실제 도구 결과, 출처, 조회 실패·미수행 구분 |
| 권한·협업·변경 관리 | 15 | 직무 경계, 승인·담당자 안내, 검증·복구 |
| 전후 비교와 비용 인식 | 20 | 같은 입력의 비교, 사용 스킬·세션·토큰 변화, 한계 |

제출물은 다음으로 통일할 수 있습니다.

- 과제 질문, 고정 입력 자료와 기준 시각.
- 수정 파일 및 변경 전후 차이.
- 이전·이후 요청 ID와 실행 ID, 핵심 도구 증거.
- 결과 비교표, 효과가 없거나 부작용이 생긴 이유.
- 미구현 도구·자료 부족·권한 제한과 다음 개선안.

`infraops`의 수용 기준 검사는 구현된 항목에 한해 실제 랩 상태를 평가합니다. 모델 운영의 규칙 기반 평가는 정해진 품질 신호를 측정합니다. 이 둘과 기존 `assessor`를 모든 자유형 에이전트 과제의 완성된 자동 채점기로 취급하지 않습니다.

## 8. 일상 운영·중지·복구

수업 전에는 서비스 상태, 러너 heartbeat, 인증, 남은 세션 예산, 남아 있는 장애·승인 대기, 로그 보관 범위를 확인합니다.

```bash
cd ~/work/kt66
docker compose -f docker-compose.yaml ps -a
python3 agents/cc-runner --status
systemctl --user status kt66-runner.service
journalctl --user -u kt66-runner.service -n 80 --no-pager
```

로그와 증거를 공유할 때 키·계정·내부 접속 자료를 확인합니다. 화면 마스킹이 임의의 모든 비밀을 찾아주는 것은 아닙니다.

### 사용량 관리

평시 감시 5개는 코드로 관측하고 정상·무변화에는 AI를 호출하지 않습니다. 기본 10분에서 변화가 계속되면 5·2·1분으로 짧아지고 안정되면 복귀합니다. `poll_seconds: 5`는 큐 확인 주기이며 “5초마다 모든 근무자 모델 호출”이라는 뜻이 아닙니다.

별도 예약 루프와 사용자 대화는 세션을 사용합니다. SOC 종합 보고 기본값은 KST 09:00·18:00입니다. 필요하면 cadence를 하루 한 번으로 조정하고, 사용량 비교는 같은 업무·입력·기간으로 진행합니다. `max_tokens`가 CLI 전체의 강제 토큰 중단 한도라고 가정하지 않습니다.

### 설정·인증 변경

- 지침·조직·루프를 바꾸면 새 하네스와 활성 상태를 확인합니다. 운영 자료와 생성 사본은 직접 고치지 않습니다.
- `API_KEY` 등 컨테이너 환경을 바꾸면 `./kt66.sh up`으로 변경된 서비스를 재생성합니다. 단순 `restart`는 새 환경변수를 적용하지 않습니다.
- CLI 인증은 같은 사용자로 갱신합니다. 서비스 PATH를 바꿨다면 `daemon-reload` 후 유휴 시점에 러너를 재시작합니다.
- 역할·자산 범위가 바뀌면 이전 대화의 “항상 허용”은 다시 승인해야 할 수 있습니다. 대화 승인은 직무 밖 권한을 열지 않습니다.

### 수업 종료

진행 중 작업을 정리하고 주입을 원복한 뒤 필요에 따라 러너와 스택을 중지합니다.

```bash
systemctl --user stop kt66-runner.service
./kt66.sh down
```

`down`은 컨테이너와 네트워크를 내리며 기본적으로 named volume을 남깁니다. **`./kt66.sh down -v`는 볼륨 데이터를 삭제하므로 일반 수업 종료나 문제 해결 명령으로 사용하지 않습니다.**

학생의 원본 지침 변경은 Git 차이 또는 파일 사본으로 보존합니다. 요청·증거·SQLite·모델 운영 데이터·Docker 볼륨은 별도 실행 데이터입니다. 백업은 관련 기록 쓰기를 멈춘 상태나 SQLite 일관성 백업 방식으로 수행합니다. 자격증명은 다른 학생의 복제 이미지에 포함하지 않습니다.

원복은 이번 수업에서 바꾼 파일·주입·변경안만 대상으로 합니다. `git reset --hard`나 전체 실행 데이터 삭제로 다른 학생·회차의 증거까지 지우지 않습니다.

### 자주 발생하는 문제

| 증상 | 먼저 확인할 곳 |
|---|---|
| 웹앱은 열리는데 NOC가 안 열림 | `INT_HOST_IP`가 원격에서 접근할 수 없는 과거 dummy IP인지, 서버 방화벽·바인딩 확인 |
| 강사 키가 틀렸다고 나옴 | `.env`의 `API_KEY`, 키를 읽는 컨테이너 재생성 여부, 브라우저에 입력한 값 |
| 화면은 정상인데 근무자가 움직이지 않음 | 사용자 서비스 설치·상태, 로그인 계정, PATH, 큐·한도 대기 |
| CLI를 못 찾거나 yaml import 실패 | 사용자 서비스의 PATH·Python 경로와 PyYAML 설치 |
| 디스크 질문에 권한이 없다고 함 | 시스템 담당 선택 여부, 실제 도구의 승인 대기인지 직무 밖 거부인지 |
| 자료가 비었는데 정상이라고 답함 | 보관 기간·수집 공백·조회 오류와 해당 스킬의 보류 기준 |
| 스킬을 수정해도 변화가 없음 | 역할 연결·스킬 선택·로드한 버전·새 대화 여부 |
| 세션이 중간에 권한 오류로 끝남 | 실행 중 역할·연결 스킬·직무 정책 변경 여부 |
| GPU 지표가 안 보임 | 선택 구성인 터널·외부 서비스·수집 경로의 연결 여부 |

상세 진단과 승인 흐름은 [운영 매뉴얼](AGENT-OPERATIONS.ko.md), 통제 범위와 남은 위험은 [보안 설계](agent-security-design.ko.md)를 참고합니다.
