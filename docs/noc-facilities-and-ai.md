# NOC의 시설 배치와 AI 장비 관찰

NOC에서 설비·장비를 선택하면 **설계값, 시뮬레이션 값, 실물 조회 결과**를 구분해 읽을 수 있습니다. 그림은 자산을 찾고 계통을 이해하기 위한 교육용 개념 배치이며, 실측 건축 도면이 아닙니다.

## 실내와 옥외 시설

상단의 **옥외** 버튼은 별도 부지 화면을 엽니다. 전체 보기에서도 건물 옆에 독립적으로 표시하며, 5층이나 1층의 일부로 취급하지 않습니다.

| 배치 | 설비 | 이 훈련장의 배치 가정 |
|---|---|---|
| 옥외 | 수전 인입, 변전소, 비상 발전기, 연료탱크 | 인입·배기·방열·연료 계통을 실내와 구분 |
| 옥외 | 냉각탑 2대, 축열·보충수 탱크, 외기 관측 | 외기에 열을 방출하는 냉각 단계와 경계 조건 |
| 옥외 | 태양광, BESS, 연료전지, 경비 초소 | 옥외 패키지형 전원과 부지 진입 경계 |
| B1 전기실·배터리실 | 개폐기, 변압기, ATS, UPS, 배터리 | 이 설계는 실내 전기실·배터리 구역을 가정 |
| B1 기계실 | 수랭식 냉동기, 펌프, 열교환기, 수 이코노마이저 | 옥외 냉각탑과 연결되는 실내 수 계통 |
| B1 방호·매체 폐기 구역 | 소화용기, VESDA, 매체 파쇄기 | 전기·배터리 방호와 매체 폐기 작업 공간 |
| 1F 보안 로비 | 정문, 검색대, 맨트랩, CCTV, 소방 수신반 | 안내·대기 → 검색 → 인증 → 계단·승강기 |
| 전산실 | PDU, 부스바, 항온항습기, 인로우 팬코일 등 | 담당 랙·아일에 대응 |

변압기, BESS, 발전기, 탱크 등은 실제 설계에 따라 실내·옥외형이 달라집니다. 여기서는 위 가정을 채택했습니다. 액체 냉각 설비는 고밀도 데이터센터 비교 실습용이며, 실물 DGX Spark·Jetson Thor에 액체 배관이 설치되어 있다는 의미가 아닙니다.

시설 상세에는 다음을 표시합니다.

1. 설비 역할과 배치 이유
2. 전력·냉각·소방·물리보안 계통에서의 위치와 관련 설비
3. 현재 시뮬레이션 상태와 설계·설정값
4. 이상이 미치는 영향과 점검할 내용

항온항습기의 **아일 냉방 합계**는 해당 장치의 개별 실측 출력이 아닙니다. 플랜트 전체 용량도 개별 냉각탑의 출력과 다릅니다. 개별 계측이 없는 설비는 미연동으로 표시합니다. 실내의 이중마루·격리 구조·콜드플레이트는 독립 상자로 그리지 않으며 **자산 목록**에서 상세를 확인할 수 있습니다.

### 로비와 지하의 동선

**1F는 로비만**, 전력·기계 주 설비는 **B1**에 둡니다. 로비는 방문객 대기석과 안내 데스크를 출입 검색선 옆에 배치합니다. 정문은 외벽의 개구부이며, 검색대를 지나 인터록 포털에서 인증한 뒤 계단·승강기로 이동합니다. CCTV는 출입 동선을 향하는 벽부형, 소방 수신반은 안내 담당자가 확인할 수 있는 벽면에 표시합니다.

지하에는 전기실·기계실·배터리실·소화용기실·매체 폐기실을 구분하고, 공통 복도로 연결합니다. UPS·배터리 캐비닛과 냉동기 앞의 빗금 영역은 점검 공간입니다. 인원 출입은 녹색, 반입·점검 동선은 황색 화살표로 표시합니다. 문에는 개구부와 개폐 방향을 표시하며, 지하의 낮은 문틀·벽은 내부 장비가 가려지지 않도록 자른 단면 표현입니다. 실제 문이나 벽 높이를 뜻하지 않습니다.

시설 담당은 B1, 물리보안 담당은 1F에 배치됩니다. 위치를 바꾸어도 설비 ID와 전력·냉각 연결 관계는 유지하며, 권한은 담당 직무의 상한을 따릅니다. 모든 치수와 이격은 상대적인 화면 좌표입니다. 실제 건물의 시공·피난 도면이나 제조사 설치 치수로 사용할 수 없습니다.

### 외형 참고 자료

일반 상자 대신 수랭식 냉동기의 수평 용기·압축기, 모터와 펌프 케이싱, 건식 변압기 외함·코일, 모듈형 UPS·배터리 캐비닛, 곡면 유리 인터록 포털을 구분했습니다. 대표적인 제품 구조는 아래 제조사 자료를 참고했습니다. 특정 제품의 성능·용량을 훈련 자산의 정격으로 가져온 것은 아닙니다.

### 학생이 고치는 파일

| 파일 | 수정할 내용 | 화면·동작의 변화 |
|---|---|---|
| [assets.yaml](../envsim/assets.yaml) | 설비 종류, 정격, 연결 대상, 층, `location`, `site_pos` | 배치와 시뮬레이션 입력 변경 |
| [facility-guide.yaml](../envsim/facility-guide.yaml) | 역할, 배치 이유, 고장 영향, 점검 항목 | 시설 상세의 한국어 학습 설명 변경 |
| [model.py](../envsim/model.py) | 전력·냉각·경보 계산 | 시뮬레이터 동작 변경 |
| [facility-floor.js](../noc/static/facility-floor.js) | B1/1F 방 구획, 문, 점검 여유, 동선, 설비 크기와 배치 이유 | 층별 건축 배치와 설명 변경 |
| [facility-scene.js](../noc/static/facility-scene.js) | 설비 종류별 SVG 형상 | 설비 그림 변경 |

B1/1F의 방·문·동선을 바꿀 때는 `facility-floor.js`의 배치 좌표와 `assets.yaml`의 해당 설비 `pos`를 함께 맞춥니다. 새 설비는 방과 점검 여유를 정한 뒤 배치표에 등록합니다.

예를 들어 냉각탑은 `floor: null`, `location: outdoor`, `site_pos: [0.7, 5.5]`로 배치합니다. 연결된 냉동기의 `condenser` ID는 유지하므로 위치만 바꾸어도 계통 관계가 끊기지 않습니다.

학습 과제로 냉각탑 정지 → 플랜트 가용 용량 감소 → 아일 온도 변화를 관찰하고, 냉동기 고장과 구별할 근거를 `checks`에 정리할 수 있습니다. 자연어 설명 수정만으로 물리 계산이 달라지는 것은 아닙니다. 설명은 `facility-guide.yaml`, 계산의 입력은 `assets.yaml`, 계산식은 `model.py`에서 각각 변경합니다.

시설 설명은 저장소의 계통 정의와 계산 모델을 근거로 작성했습니다. 별도 참고 원문을 반영할 때는 실제로 확인한 출처와 모델의 지원 범위를 함께 기록합니다.

## NVIDIA AI 전산실

3층 전용 캐비닛에 DGX Spark 5대와 Jetson Thor 2대를 표시합니다. 금색 Spark와 검정 Thor를 구분하며, 관리용 GPU 게이트웨이는 별도 슬롯입니다. 2026-09-23 신규 장비 6대의 하드웨어와 서비스를 읽기 전용 SSH로 확인했습니다.

| 자산 | 제품 | 관리 주소 | SSH |
|---|---|---|---|
| `dgx-spark-01` | 기존 DGX Spark | 내부 터널 `10.20.50.10` | 기존 대장 설정 유지 |
| `dgx-01` | DGX Spark | `211.170.162.110` | 8022 |
| `dgx-02` | DGX Spark | `211.170.162.111` | 8022 |
| `dgx-03` | DGX Spark | `211.170.162.112` | 8022 |
| `dgx-06` | DGX Spark | `211.170.162.113` | 8022 |
| `thor-02` | Jetson AGX Thor | `211.170.162.120` | 8022 |
| `thor-03` | Jetson AGX Thor | `211.170.162.121` | 8022 |

신규 6대의 `gpu-external`은 외부 관리 구분입니다. 내부 `app` 서브넷이나 FW–IPS 경로에 편입되었다는 의미가 아닙니다. SSH 비밀번호는 저장소와 NOC에 보관하지 않습니다. GPU 담당의 자산 조회 범위에만 ID를 추가했고, 다른 역할의 권한을 확대하지 않았습니다.

### 클릭해서 확인하는 내용

- **접속 상태:** 로그인 없이 SSH TCP 8022 포트 응답만 60초 간격으로 확인합니다. 로그인·GPU 정상 여부를 보장하지 않습니다.
- **서비스 현황:** 등록된 플랫폼, API 주소, 조회 상태와 시각을 표시합니다.
- **설치·서빙 모델:** Ollama 설치 목록과 다른 플랫폼의 제공 모델 목록을 구분합니다. 기본 5개를 표시하고 나머지는 펼쳐봅니다. 적재 모델이 설치 목록에도 있으면 우선 표시합니다.
- **Ollama 적재 모델:** `ollama ps`에 대응하는 `/api/ps` 결과로 메모리·GPU 배치량·컨텍스트·적재 만료 시각을 표시합니다. 적재 중인 모델이 없다는 사실과 조회 실패를 구분합니다.
- **하드웨어:** OS, CPU, 통합 메모리, GPU, 저장장치, 드라이버와 등록 시점 점검 기록을 표시합니다.

신규 6대는 모두 Ollama가 확인됐습니다. Thor 2대의 vLLM은 8001 포트에 있고, Thor 03에는 별도 임베딩(8016)·재정렬(8015) API도 있습니다. 이 두 서비스는 독립 `/health` 응답을 사용하며, vLLM 컨테이너 이미지를 사용했다는 이유로 표준 vLLM API라고 표시하지 않습니다.

모델 조회는 **선택한 장비에 한해** NOC 서버가 실행하고, 여러 브라우저의 요청을 60초 캐시로 합칩니다. 조회만으로 모델 생성·적재·다운로드를 요청하지 않으므로 추론 토큰을 소비하지 않습니다. 닫힌 장비를 위한 별도 모델 조회 루프는 없습니다. 기존 내부 DGX는 envsim의 기존 OT → IPS → GPU 게이트웨이 경로로 위임하고, 외부 6대는 NOC에서 대장 IP로 조회합니다. 새 우회 경로나 네트워크 권한을 만들지 않습니다. 브라우저는 NOC API에만 접근하므로 모델 서버의 CORS 설정을 바꿀 필요도 없습니다.

Spark·Thor는 CPU/GPU 통합 메모리를 사용합니다. `/api/ps`의 GPU 배치량을 별도 전용 VRAM 용량으로 오해하면 안 됩니다. vLLM·llama.cpp의 `/v1/models` 응답은 서빙 목록이며, 메모리 상주·사용량은 별도 관측이 없으면 미수집으로 표시합니다. 접속 실패·인증 필요·빈 목록도 서로 다르게 표시합니다.

### 서빙 플랫폼 추가

장비의 `serving`에 **실제로 확인한** 서비스만 등록합니다. 다음은 설정 형식의 예이며, llama.cpp가 이미 설치되어 있다는 뜻이 아닙니다.

```yaml
serving:
  - id: ollama
    platform: ollama
    name: Ollama
    port: 11434
    purpose: 로컬 모델 추론
  # 실제 llama-server가 이 포트에서 응답할 때만 추가
  - id: llama
    platform: llama.cpp
    name: llama.cpp
    port: 8080
    purpose: GGUF 모델 서빙
```

지원 어댑터는 `ollama`, `vllm`, `llama.cpp`, `openai`, `health`입니다. `health`는 이 프로젝트에 등록된 커스텀 서비스의 `GET /health` → `{ok: true, model: "..."}` 형식을 위한 것입니다. 일반적인 모든 health API를 자동 해석하지는 않습니다. 대상 IP와 포트는 자산 대장에서만 읽으며, 브라우저가 임의 URL을 지정할 수 없습니다. 리다이렉트를 따라가지 않고 응답 크기도 제한합니다.

인증이 필요한 서비스는 현재 인증 필요로 표시합니다. 플랫폼 키를 자산 대장에 적어 해결하지 마세요. 인증 연동은 서버 측 비밀 관리와 조회 전용 권한을 별도로 설계해야 합니다.

설치 모델의 파일 크기와 현재 메모리 사용량도 구분합니다. 새 장비의 GPU 사용률·전력은 아직 주기적으로 수집하지 않습니다. 이들의 전력 `0 kW` 설정은 **환산 전력 합계에서 제외하기 위한 값**이며, 실제 소비전력 0이라는 뜻이 아닙니다.

## 설정 반영과 검증

정적 SVG·화면 코드는 새로고침으로 반영됩니다. 자산 대장과 시설 설명은 envsim 시작 시 읽으므로, 실습이 진행 중이지 않을 때 반영합니다. envsim 재시작은 메모리 안의 고장·시뮬레이션 상태를 초기화합니다.

```bash
docker compose -f docker-compose.yaml up -d --build --no-deps envsim noc
```

NOC의 자산 대장 캐시도 새로 시작하며, 기존 브라우저는 새로고침합니다. GPU 역할의 자산 범위를 바꾸면 역할별 권한 설정과 명단을 함께 수정하고 하네스를 다시 컴파일합니다.

검증은 `noc/tests/test_ai_services.py`, `test_remote_hosts.py`와 브라우저 시나리오 `facility-ai-browser.cjs`, `facility-floor-browser.cjs`를 사용합니다. 층별 자산 누락, 장비·통로 간섭, 마우스·키보드 선택, 화면 크기별 맞춤을 함께 확인합니다. 시뮬레이터 객체 안에서 고장 연쇄를 검사하며 운영 장비에 고장이나 모델 작업을 주입하지 않습니다.

API 의미의 기준: [Ollama 설치 모델](https://docs.ollama.com/api/tags), [Ollama 적재 모델](https://docs.ollama.com/api/ps), [vLLM 서버](https://docs.vllm.ai/en/latest/serving/online_serving/openai_compatible_server/), [llama.cpp 서버](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
